# 学びの保存と活用

## 概要

セッションはエフェメラル（コンテナは消える）なので、作業中に得た学びは
コミット対象のナレッジベースに残さない限り次回ゼロからやり直しになる。
このスキルは「学びの捕捉 → 正しい置き場所への振り分け → 次回の再利用」を仕組み化する。

## 保存する価値がある学びの基準

次のどれかに当てはまるものだけ保存する（作業ログは対象外）:

1. **環境のクセ**: ツールの制約・エラーと回避策（例: WebFetchが403 → WebSearchスニペットで代替）
2. **失敗と再発防止**: 一度ハマって解決した問題と、次回の正しい手順
3. **業務知識**: 可能性ラボの事業・市場・規制に関わる新事実
4. **手順の改善**: 既存ワークフローより速い・確実なやり方を発見したとき

「またこれを調べ直すことになるか？」が Yes なら保存。No なら保存しない。

## 手順

### Step 1: 学びを1〜3行に圧縮する

「状況 → 何が起きた → どうすれば良い」の形に絞る。長文の経緯は書かない。
日付を必ず付ける（鮮度判定に使う）。

### Step 2: 置き場所をルーティングする（最重要）

| 学びの種類 | 置き場所 |
|---|---|
| 特定スキルの作業でだけ使う学び | **そのスキルの SKILL.md の Gotchas か references/** に直接追記 |
| 複数スキル・全作業に効く環境のクセ | `knowledge/environment.md` |
| 可能性ラボの事業・市場・規制の知識 | `knowledge/domain.md` |
| 作業手順・段取りの改善 | `knowledge/process.md` |

- 既存スキルに追記した場合、knowledge/ 側には書かない（二重管理しない）。
  横断的に参照されそうなら knowledge/ にポインタ1行だけ置く。
- ユーザー固有のメモリ（応募履歴・実績など）は各スキルの `logs/`（gitignore対象）へ。
  **学びはコミット対象、個人記録はローカル** が境界線。

### Step 3: 重複チェックと更新

追記前に保存先ファイルを読み、同じ学びがあれば新規追加ではなく
**既存エントリを更新**する（日付を新しくし、内容を上書き）。
矛盾する古い学びを見つけたら `~~打ち消し線~~` ではなく削除して書き直す。

### Step 4: コミット

knowledge/ や SKILL.md への変更はコミットして初めて次セッションに届く。
作業全体のコミットに同梱でよい（学びだけの単独コミットは不要）。

## 学びの「使う側」の手順

- 関連する作業を始める前に `knowledge/environment.md` を読む（環境のクセは全作業に効く）
- リサーチ・案件・SNS系の作業なら `knowledge/domain.md` も読む
- 過去の学びが現状と食い違っていたら、その場で更新する（読むだけで放置しない）

## エントリの書式

```markdown
- **YYYY-MM-DD**: [状況] → [事実/回避策]。（根拠や実装場所があれば1行）
```

## Gotchas（必読）

- ⚠️ 「全部 knowledge/ に書く」は失敗パターン。スキル固有の学びは
  そのスキルに書かないと、次回そのスキルを使うとき読まれない
- ⚠️ 日付のないエントリは鮮度判定ができず信頼できない。必ず日付を付ける
- ⚠️ 学びは「再利用できる形」で書く。「CrowdWorksでエラーが出た」は学びではなく、
  「CrowdWorksはWebFetchを403で拒否する → WebSearchスニペットで代替」が学び
- ⚠️ knowledge/ が長くなったら整理する（100行超えたら陳腐化エントリを削る）。
  追記専用ファイルにしない

## 参照

- 環境のクセ → `knowledge/environment.md`
- 事業・市場・規制の知識 → `knowledge/domain.md`
- 手順の改善 → `knowledge/process.md`
